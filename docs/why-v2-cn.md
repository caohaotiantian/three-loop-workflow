# 我们为什么重写 three-loop-workflow

*这次重写起因于一句「太费 token」的抱怨,中途变成一次测量,最后两次推翻了它自己的计划。*

English → [why-v2.md](./why-v2.md)

---

## 那句抱怨

这个 skill 烧 token 太快了。

整个立项理由就这一句。**不是**「纪律不对」—— 纪律经过 14 个版本的打磨,是好用的。问题在于:遵守它已经贵到让人不想遵守。

首先要老实讲的一点是:**这次重写并没有回答那句抱怨。** 它回答的是一个邻近的、能被测量的问题。下文所有关于体积的数字都是**表面体积** —— skill 有多少词 —— 而不是跑完一个任务的实际成本。至今没有人用 v2 跑过一个真实功能并端到端测量它的开销。这个缺口在这里写明,而不是含糊过去,因为它是这项工作最大的一处未知。

而测量真正查出来的东西,比 token 问题更糟 —— 下文讲的就是这个。

---

## 第一部分 —— v1 到底出了什么问题

### 棘轮

v1.14.0 那个每次都要加载的 `SKILL.md` 是 **2,915 词**,而它自己的一致性门禁把上限设在 2,920。经过 14 个版本的刻意精简,只剩 5 个词的余量。

它之所以永远瘦不下来,是因为有两个机制在往相反方向拉。门禁**硬性要求 10 个特定 token 必须物理存在于** `SKILL.md` 里 —— `blast-radius`、`change-orphan`、`clean-first-round`、`two-generation`、`zero severe`,还有另外五个。同一个门禁又**给这个文件的词数封顶**。一个机制把内容往里塞,另一个机制因为内容在那里而惩罚它。上限此前已经被抬高过一次:2,888 → 2,920,就为了腾地方。

这不是一个能精简的文件,这是一个棘轮。这也是为什么这件事变成了重建,而不是修改。

围绕它的还有整个包体:**15 个 Markdown 文件、21,802 词散文** —— 把 5 个脚本一并计入,则是 20 个文件、27,896 词。而在产品旁边还有「尾气」—— `docs/design/` 和 `docs/implementation/` 这套提交进仓库的每任务归档,**43,822 词**。是它所记录之物的一倍半,而且没有任何人类读过。agent 写、agent 读,然后进入每一个使用这个 skill 的仓库。

### 那个门禁是摆设

`CLAUDE.md` 把 `check-consistency.sh` 称为「权威验收检查」。它一共 242 行,其中 124 行是实质代码,而它只有**一种**检查原语:一个名为 `require()` 的 shell 函数,函数体整个就是 `grep -qF -- "$token" "$f"`。它被调用了 **24 次**。与之相对,真正检查**内容**的检查只有 **5 个**:两次对重复代码块的逐字节比对、一次针对特定禁用字符串的 grep,以及两个字数上限。

于是我们测了它。我们把 `SKILL.md` 的核心终止规则替换成语义完全相反的一句 ——「*立即退出循环;确认轮是可选的*」—— 同时把它要求的 token 留在一个 HTML 注释里。然后运行门禁:

```
three-loop-consistency: OK
EXIT=0
```

门禁分辨不出一条规则和它的反面。**一个词出现,不等于一条规则存在** —— 而一个几乎全部由 `grep -qF` 搭起来的门禁,除了存在性检查之外不可能是别的东西。

### 测试什么都没测

`tests/scenarios/` 有 33 个行为 fixture,连续 16 个版本亮着绿灯。

它从来没有跑过对照组。于是我们跑了一次:6 个 fixture,每个回答两遍 —— 一遍由加载了 skill 的 agent 回答,一遍由一个**被硬性禁止阅读它**的 agent 回答。总共 12 次运行。

| 臂 | 结果 |
|---|---|
| 加载 skill | 6/6 正确 |
| 屏蔽 skill | 6/6 正确 |
| **区分度** | **0/6 —— 0%** |

被要求自陈时,12 次运行**全部**主动承认:场景正文在提问之前就把适用规则说出来了。抽查的 9 个文件,9 个都有同样的缺陷。有些文件名本身就是答案 —— 一个叫 `quickly-add-is-full.md` 的 fixture 根本不需要打开。

**一个在行为出错时也无法失败的测试套件,比没有套件更糟**,因为它读起来像是覆盖率,而那个覆盖率并不存在。这一套连续 16 个版本报告着它从未拥有的覆盖率,而那个「检查」它的门禁,只验证了**文件存在**。

## 第二部分 —— 推翻计划的那次测量

### 我们原本打算删掉什么

v1 强制一轮确认评审:一个循环必须在「干净的一轮」之后再来「干净的一轮」才能关闭。这很贵 —— 它让每份产物的评审成本翻倍。

三个独立来源都说该砍:

- **Anthropic 的 Opus 5 指南** ——「移除它们」;「不要用 subagent 去验证或复查你自己的工作」。
- **superpowers 的 5×5 A/B**,结论是没有收益。
- **我们自己的研究 + 审计扫描**,其综合结论是:*删掉 two-generation 规则、删掉面板、删掉 accept 角色;diff 上保留一名评审者即可。*

计划就是照着删写的。执行之前,我们先测了一下。

### E2 —— 评审者方差

> **关于本节证据的说明。** 下面 E2 与裁决环节的数字,是在一次工作会话中测得的,而原始产物 —— 那 116 条发现、232 次裁决判定、以及用 Python 做的重新计算 —— 从未提交进本仓库。承载摘要的 `v2/README.md` 也在 v2 promotion 时被删除。因此**你无法从本仓库复现或反驳这些数字**;本文其余部分的体积与禁令计数则不同,它们在每次验收运行时都会被重新计算。一篇主旨是「无法验证的断言会一路传播」的文章,理应指明它自己哪些断言无法验证 —— 就是这些。

从 `docs/design/` 取 4 份真实设计文档。每份配 3 名独立的全新评审者,全部收到**逐字节相同的提示词**,读**同一份未改动的文档**。共 12 次评审。

它们产生了 116 条发现实例,归并后是 **70 个不同缺陷**。

| | 找到的缺陷 | 覆盖率 |
|---|---|---|
| 仅评审者 1 | 38 / 70 | **54%** |
| 评审者 1 + 2 | 60 / 70 | **86%** |
| 三人合计 | 70 / 70 | 100% |

比总数更重要的是分布。只有 **19%** 的缺陷被三个人同时发现,**51% 只被其中一个人发现**。评审者并不是先收敛到同一批缺陷、再去争论长尾 —— 他们漏掉的是**不同的**东西。单人检出率大约 55%。

还有一个关于严重度的发现:评审者 1 找到 8 个严重缺陷;评审者 2 和 3 另外找到 **4 个评审者 1 完全漏掉的严重缺陷 —— 每份文档各一个**。其中一个,正是对这个 skill 自己那条「作者绝不评审自己产出」不变式的悄悄放宽。

第 3 名评审者又多找到 10 个缺陷 —— 占并集的 14%,而第 2 名贡献的是 31%。曲线在那里变平。

**数据说:留着。** 计划错了,而那三个建议删除的来源,回答的是另一个问题。调和它们的边界是:***自我*验证已经死了** —— 一个 agent 重读自己的推理毫无增益;而***独立*评审** —— 一个从未见过那段推理的读者 —— 会把覆盖率抬高 29 个百分点,大约相当于第一名评审者所漏掉部分的三分之二。Opus 5 的指南说的是前者,这次测量说的是后者。

于是 v2 保留了确认轮,并重新机械化了它:**Deep 档两名评审者并行,Standard 档一名,绝不三名。**

### 给验证做验证

54% → 86% 这种跳跃,恰恰是那种「好看到不该轻信」的数字。它完全依赖于「评审者 2 的额外发现是**真缺陷**而不是灌水」—— 而没有人核实过。

于是,全部 116 条发现被哈希、剥离归属、确定性打乱,然后交给**每份文档 2 名独立的对抗式裁决者**复判 —— 8 名裁决者、232 次判定 —— 每人都被要求**去反驳**,并在拿不准时**默认判 FALSE**。评分标准是刻意偏向于否定我们想要的结论的。随后覆盖率由 Python 重新计算(而非由 agent 计算),并对**所有**评审者顺序取平均,而不是取某个任意的「评审者 1」。

| | 原报告 | 验证后 |
|---|---|---|
| 1 名评审者 | 54% | **56.5%** |
| 2 名评审者 | 86% | **85.5%** |

规则站住了。裁决者之间的一致率为 84%。

但这次验证暴露出第一次分析根本看不到的东西。**评审者的精确率很差:**

| 被判为…… | 经得起裁决的比例 |
|---|---|
| severe / blocking | **50–70%** |
| general / non-blocking | **30–46%** |

评审者报上来的东西 —— 包括它们标为 blocking 的 —— 有四分之一到一半并不存在。这就是「把召回率提上去」所付出的代价。让评审者「保守一点」并不能解决这个问题:被要求保守的评审者会**少报**,包括少报真缺陷。

### 那个发现制造出来的 bug

v2 刚刚定稿的 `phase.js`,是根据**原始的** blocking 计数来判定收敛的。

在 30–50% 的 blocking 发现是幻影的前提下,这是一个活着的 bug:一条并不存在的发现会消耗一轮修复,而足够多的幻影会耗尽轮次上限,并对**本来就正确**的代码宣告死锁。这与我们刚刚编目的 v1 bug 属于同一类 —— 而且是我们自己在「本该修掉这一类问题」的重写里引入的。

于是有了 v2 的 **Triage(分诊)** 步骤,位于评审与收敛之间:把每条发现对照它所引用的代码核实,驳回误读的那些。收敛判定基于**已确认**的发现,绝不基于原始报告,也绝不基于评审者的结论性措辞。承载这条规则让 `SKILL.md` 多了约 90 词,而它是这次测量买到的最有分量的一件东西。

### 轮次计数器

顺带查出来的:v1 的 runner **无条件**递增轮次计数器,位置在「是否真的执行修复」这个分支**之前**。散文写的是「R 只在有修复时递增」,代码不是这么做的。这个问题自 2026-07-07 起就已知,被拆到后续周期,然后从未发布。

我们写了一个 harness 来真实执行两个脚本的控制流:

| 场景 | v1 | v2 |
|---|---|---|
| 第一轮评审干净 | 通过,0 次修复 | 关闭,第 1 轮 |
| 1 个问题,然后干净 | 通过,accept 预算 **0** | 关闭,第 2 轮 |
| 2 个问题,然后干净 | **cap-exhausted** | 关闭,第 3 轮 |
| 3 个问题 | cap-exhausted | cap-exhausted |

一条 general 发现就让 accept-fix 预算归零。两轮修复之后,一个**完全干净的第 3 轮**被报成 cap-exhausted。在 v2 里,`round` 只在真正执行修复时才递增。

## 第三部分 —— v2 是什么

| | v1.14.0 | v2.0.0 |
|---|---|---|
| `SKILL.md` | 2,915 词 | **1,336 词** |
| 全部散文(仅 Markdown) | 21,802 词 | **6,047 词** |
| 文件数(含脚本) | 20 | **8** |
| 每任务提交文档 | 2 | **0** |

**Plan → Build → Close。** L1 与 L2 本来就是一份计划被人为切成两半。合并之后,slug 协议、回滚协议、Deprecated 章节约定,以及一整个评审循环都被删除。产出是受 gitignore 的 `.agent/<task>/plan.md`(每个任务一个目录),而不是两份提交进仓库的文档。

**深度按影响半径与可逆性分档。** *如果这件事做错了,会波及多少?撤销它有多难?* Direct / Standard / Deep,深度档配一份**清单**。v1 的判定是一堆定性谓词的析取,并且没有规模项,所以常规工作总是落到昂贵的那一支。

**门禁先于 agent。** typecheck、lint、build、test —— 在派出任何评审者之前跑完。v1 只在一处括号里提过一次。让 agent 去评价一段根本编译不过的代码毫无价值,而编译器是免费的。

**Deep 档两名评审者,Standard 档一名;先分诊,再计数。** 依据如上。

**被删除的东西,每一项都给出理由:** 五投票者面板及其反通胀条款;独立的 accept subagent(它被禁止做判断,而紧接着的下一条规则又宣布它的报告不充分);提交进仓库的每任务归档;`check-consistency.sh`;以及最后由项目所有者拍板删掉的两个 hook 脚本。v2 不再机械强制任何东西,并且明说这一点,而不是暗示一个它并不提供的保证。

**一个能够失败的测试套件。** 每个 fixture 都跑两条臂。两臂都答对的 fixture 被报为 **INVALID**,而不是绿灯。

## 第四部分 —— 那个让人不舒服的结果

新套件是有效的。但它同时说出了关于这个产品的一些不中听的话。

7 个 fixture 里,**只有 1 个产生区分度**。其余 6 个是 guard —— 模型本来就能答对、fixture 的存在是为了抓住 skill 把事情**变糟**的情形。6 个 guard 全部守住。

那个唯一产生区分度的是 **s04**:一个涉及 4 个文件的变更,其中一个角落触及了生产写入路径。对照臂把**整个**变更升到了最深档,理由是「一个变更的安全性取决于它最危险的那个组件」。skill 臂跑了 Standard,并只把那个角落单独上报。

另外 6 个是为测试评审者数量、并集规则、按计数收敛、事实与决策之分而写的 —— 而一个完全没有 skill 的称职工程师,每一道都答对了。

**在 Opus 5 之下,这套纪律的大部分与模型自身的判断是重复的。**「派评审者之前先跑门禁」「不要掩盖 flaky 测试」「仓库里已有的值要去查而不是去问」—— 这些在 2026 年是资深工程师的基线行为,写下来不改变任何事情。

真正留下来的,是那些**具体且反直觉**的规则:一个确切的评审者数量、两个都说得通的档位之间的裁决规则、「一个高风险的局部不会把整个变更升档」。

有两个 fixture,s02 和 s07,原本是按区分性写的,经过三轮调整仍然失败,于是被降级为 guard。这次降级被逐字记录在 `expected.json` 里,而不是悄悄换个标签 —— 把一个 fixture 的类别一路调到套件变绿,正是这个套件存在的目的所要防止的那种不诚实。

## 第五部分 —— 我们在构建过程中犯的错

这一节之所以存在,是因为一份只报告成功的重写文档,与一个只会报告 OK 的门禁属于同一个文体。

**我们对自己的脚本发布了一条虚假声明。** `platforms.md` 声称随包的提交 hook 会拒绝提交信息里的 AI 署名。脚本里根本没有这个检查。`feat: generated with Claude Code` 顺利通过,退出码 0。而这条声明,恰恰写在那个训诫「不要写无效检查」的文件里。它后来变成了一条永久的工程规范:**没有测过,就不要声称一个脚本会做某件事。**

**我们写了一个检查,它在自己要保障的规则上放行了。** `build.md` 规定 worktree 要放在仓库之外。而它给出的命令,是相对于**当前目录**而不是仓库根目录解析路径的 —— 所以从子目录运行时,它会悄无声息地把 worktree 建在**仓库里面**,也就是两行之下的散文明令禁止的那件事。git 会自动创建中间目录并返回 0。那个「证明」放置正确的验收检查,是靠 grep 命令里有没有 `../` —— 而这恰恰是会失效的那个假设。两名独立评审者各自实证复现了它。这与 v1 一致性门禁属于同一失败类别,由我们自己犯下,而且就发生在我们写下反对它的规范的同一次会话里。

**我们编了一个数字。** `build.md` 声称 v1 的门禁「连续 16 个版本发布」。这个数字在它所压缩的原文里根本不存在 —— 它属于另一个产物。而它被写下来的那一次 diff,正是重新措辞「陈述你跑过什么,而不是你打算做什么」这条规范的那一次。

**我们报告了一个美化自己的指标。** 禁令 token(`never`、`do not`、`don't`、`forbidden`、`must not`)在 Markdown 面上从 **135 降到 37** —— 73% 的降幅,读起来像是一次彻底改写。但禁令**密度**根本没动:**每千词 6.19 → 6.11**。绝对值的下降几乎完全是文档变短的副产品,而不是把禁令改写成正向指令的结果。更糟的是,那份对比的第一版拿 v1 的**全部文件**去比 v2 的**仅 Markdown** —— 一张表里用了两个分母。

而这个错误比它自己的修正活得更久。写这篇文章时,从重建笔记里继承来的那组数字(137 → 47)被发现**仍然**在混用口径:137 是仅 Markdown 的计数,47 是全部文件的计数。上面这组数字是用同一个正则、同一个口径,从 tag `v1.14.0` 和已发布的工作树重新测量的,并在此写明,以便下一个人能够复现或反驳。同一个指标,同一类错误,在以「测量纪律」为主题的文档里,已经发生三次了。

**我们两次冤枉了正确的代码。** 一个 harness「证明」`phase.js` 会在两名评审者只回来一名时关闭阶段。代码是对的;错的是 harness —— 而且以两种不同的方式错了两次。

到那次会话结束时,这个模式已经出现了五次,而它只有一种形状:**检查是为了确认作者所相信的东西而写的,不是为了证伪它而写的。** 结构性的修法 —— 现在已成惯例 —— 是**重新计算,而不是断言**。最终的验收脚本会重新计算每一个公布的指标,而不是与硬编码值比对;它立刻抓出了一个陈旧数字,而硬编码的检查本来会给它放行。

## 第六部分 —— 我们仍然不知道的事

- **`close.md` 未经测量。** 它是从 v1 的 F 阶段基于论证、而非基于证据继承下来的,是这次重写中测试最少的部分。
- **两名评审者的结论是在设计文档上测得的,不是在 diff 上。** 把它套用到 diff 上是一个推断。门禁已经在评审者看到代码之前消除了一整类缺陷,所以第二名评审者在那里的边际价值**可能更低**。
- **我们从未观察到一次干净的首轮评审。** E2 的 12 次评审全都发现了问题。「第一轮干净只是弱证据」是从约 55% 的检出率推出来的,并未被直接测量。
- **只有一个真正起作用的区分器。** 这个套件证明了 skill 是无害的,并证明了一条规则是有分量的。它没有测试其余部分。
- **评审者精确率是下界,不是估计值。** E2 裁决的是**历史上已关闭的**文档,所以有些 FALSE 判定属于时代错位 —— 用后来才存在的门禁去评判当时写的文档。真实使用中的精确率大概率好于 30–50%。
- **E2 的证据不在本仓库里。** 评审者方差与裁决环节的数字,测自一次工作会话,而那次会话的产物从未被提交;承载它们的摘要也在 v2 promotion 时被删除。这些数字在此本着诚实报告,但无法从仓库中核对。体积、文件数与禁令计数则可以,而且每次验收运行都会重新核对。
- **最初那句抱怨仍然没有被回答。** 这里所有的 token 数字都是表面体积。v2 跑一个真实任务要花多少,尚未测量。

## 哪些经验可以外推

如果你在维护一个 skill、一个提示词库,或任何一套「agent 应当遵守的规则」,有四点可以迁移:

1. **一个在行为出错时也无法失败的检查,比没有检查更糟。** 在你添加一个门禁之前,先写出那个应该失败的用例,并亲眼看着它失败。如果你没法让它失败,那你写的是一份挂着绿灯的文档。

2. **没有对照臂的测试不是测试。** 让每一个行为 fixture 都在**屏蔽 skill** 的条件下也跑一遍。如果一个没有你那套规则的 agent 也能答对,那么这个 fixture 测的是模型,不是你的工作 —— 而你由此学到的是关于**这条规则**的事,不只是关于这个 fixture 的事。

3. **独立评审不是自我验证,「删掉第二轮」的建议并不适用于它。** 一个人覆盖 56.5% 的缺陷,两个从未见过彼此输出的读者覆盖 85.5%;第三个人只再多 14 个百分点。

4. **要求报告一切,然后自己分诊。** 高召回的代价是低精确 —— 你拿回来的东西里,有 30% 到 50% 并不存在。**先确认再修复,而且要在计数之前确认。** 否则一条并不存在的缺陷会吃掉一轮修复,并可能在本来就正确的代码上耗尽预算。

最后一条是上面所有内容的一般形式:**先测量,再删除;然后再检查那次测量本身是不是真的。** 我们两次跳过第二步,两次都发布了 bug。
