# 为什么有 v3

*v3.0.0 从头重写了 v2,正如 v2 从头重写了 v1。这里写的是改了什么、依据是什么,以及哪些事情没有人测量过。*

English version → [why-v3.md](./why-v3.md)

---

## 提出的要求

所有者的方向:skill 应当**与运行时无关**,只要 agent 能读文件、能跑项目自己的命令、能和用户对话,它就能用。
它不应附带**任何 Workflow 脚本**,也不应点名**任何 agent 类型或工具**。它应当遵循**约定优于配置**:写明要求
与约束,把手段留给 agent。它还应当**自包含**:旁边不需要另装任何东西,项目里也不需要做任何设置。

这个方向背后是成本。所有者自己用 v2 的会话耗时长得多,派出的 agent 也多得多。那些会话没有按任务配对,也无法
从本仓库复现,所以这里没有任何内容以它们为依据。

## 仓库自己的证据说了什么

**这套纪律的大部分本来就是冗余的。** `docs/why-v2.md`(第 4 部分)记录了:一个被禁止阅读 skill 的 agent
几乎答对了每一个 fixture;唯一能区分两条臂的 fixture,是一个只有某个局部有风险的变更。提交 `c33354e` 用一个
对照臂探针重做了这件事:在 skill 被拿掉的情况下交给 agent 的规则,大多数都被不经提示地答对了,有些答出的理由
比规则本身更锐利。v3 把这些结论贯彻到了 skill 的其余部分。

**问题不在轮次上限,而在范围膨胀。** 预注册的轮次上限实验(`docs/2026-07-31-round-cap-experiment.md`)
发现,预埋的缺陷在第一轮就修好了。之后的轮次都花在了修复步骤自己加进来的机制上,下一轮评审的是这些新机制,
而不是变更本身。修复步骤什么都没加的那个重复实验,立刻就收敛了。上限维持为三。

**测试投入是被一个机制推高的,不是被选择的。** v2 从三个方向要求每一轮都写测试:Accept 要求一条用退出码
判定成败的命令;Build 循环脚本告诉每个写入者「新行为需要测试」;评审简报要求有测试。没有任何地方说过什么
时候测试是错误的检查手段。

**阅读量。** 由门禁从标签重算:在 v2.7.0 中,始终加载的 `SKILL.md` 是 2,704 词,一个 Standard 任务要读
8,725 词(`SKILL.md` 加上 plan 与 build 两份引用),整个散文面是 16,605 词。在 v3.0.0 中,`SKILL.md` 是
1,711 词,它就是 Standard 路径的全部;加上 `references/deep.md`,散文面是 2,322 词。

## 砍掉了什么,为什么

- **Build 循环脚本**(`phase.js`)及其测试框架:绑定在一个运行时上,所有者反映用户并不触发它,而且它是仓库里
  最重的门禁机制。两者都保留在 `v2.7.0` 标签上。
- **所有点名的机制。** v3 改为写明它需要的性质:评审者是一个没有写这个变更的上下文;询问用户就是问,然后等。
  有一行说明用户可以加上自己的评审、安全或编排工具,它们补充独立评审,绝不替代它。
- **配置**:anchor map 及其角色、`baseSha` 记账、进度行、驳回文件、数值化的分诊刻度。plan 写在
  `.agent/<task>/plan.md`,每个任务一个目录,随变更一起提交。`.gitignore` 里已有的 `.agent` 条目保留。
  变更描述承载交接。
- **委派长文、指南 journal、平台表。** 长文退役了:worktree、集成者、脚本的 API。留下两条性质。被委派方说的
  「做完了」是一个声明,接受之前,变更必须确实在仓库里且非空。一个有边界的领域,当阅读或改动它会填满当前上下文时,
  交给它自己的 sub-agent;简报写明领域以及它不能碰什么,当前上下文只留下结论,不留下对方的全过程。探针发现,模型处理
  「指南写错了」的情况比规则处理得更好。安装路径挪到了 README。
- **默认写测试。** 证据是「没有这个变更就会失败」的最便宜的那样东西:一个现有检查转绿、一个新测试,或者观察到的
  结果。默认不要求新增单元测试,而且 skill 点名了单元测试是错误检查手段的场合(UI 渲染、接线、配置、对外部
  服务的薄调用、一次性脚本、散文),在那些地方要观察结果。缺失的测试是 non-blocking,除非它守护的是一个已确认
  的正确性缺陷。
- **往上推的深度默认值。** v3 选能满足要求的最轻深度。Deep 只在四条收窄后的触发条件上触发;Direct 取决于
  正确性是否在改动本身中可见,或者是否已有检查钉住了它。

## 保留了什么,依据是什么

- **一个高风险的局部只升级那个局部,不升级整个变更**:这是对照臂唯一一条被测出答错的规则。
- **人会点击、输入或调用的路径**,由一个没有写这个变更的上下文来驱动。那个上下文拿到的是路径和失败的样子,
  而不是 diff,也不是作者的叙述,与 plan 矛盾的结果是一条发现。只有在没有这样的上下文时,才由作者自己驱动,
  并在交接里说明。退役单独的行为 agent 时把这条要求一起带走了;要求留下,机制不留。
- **只有用户能降低深度**,而且要在一次推荐之后:向没用过这套流程的人展示,这次变更会因此跳过什么,以及留下
  的失败是什么。如果用户坚持,agent 照做并记录下来。硬约束不因此被放弃。
- **独立评审**,用于 Direct 以上的变更,依据的是相关盲点这一论证。没有独立上下文可用时,评审作为一趟单独的
  pass 来跑,只依据 diff 和简报,标注为 "self-review, not independent",并向用户提供简报。
- **先分诊,再计数。** 把未确认的发现计入,会把修复轮次花在正确的代码上。它背后的精确率测量无法在这里复现。
- **在第一次编辑之前写好 Non-goals 与 Accept**,这是针对实验所发现的范围膨胀的防护。
- **用停止条件代替计数器。** 当一轮下来已确认的发现没有变化、一次修复延伸到计划没有点名的文件或机制、或者
  第三轮之后仍有 blocking 发现时,停下来问。新的检查、测试框架、防护或测试文件,成为一个点名的后续事项,而不是
  修复的一部分,这正对准了消耗掉实验轮次的那件事。每次修复之后,评审者只复查这次修复,这让停止条件有东西
  可数。
- **两名评审者,只用在错误会离开仓库的地方**:对外部契约的破坏性变更,或者一个不可逆的外部效果,发现取并集,
  绝不取交集。`docs/why-v2.md` 中的双评审者数字是在设计文档上而不是 diff 上测得的,而且无法在这里复现,这就是
  它被限定在这里的原因。
- **对凡是被阅读而非被运行的东西做冷读**:读成品文件,当作产品来读,而不是当作 diff。更新日志的 v2.5.0 条目
  记录了原因:那样通读那次发布,发现了一条会把空 diff 交给评审者的指令,而任何 diff 评审都看不到它。空 diff
  不是一次干净的评审。

## 尚不知道的事

- **v3 对耗时和测试量的影响没有被测量过。** v2 与 v3 之间不存在任何结果对比。上面的词数说的是 agent 要读
  多少,而不是一个任务要花多久、要写多少测试。
- **冗余性结论是有时效的。** 它们是在 2026 年年中的模型上、针对 v2 的措辞得出的,没有针对 v3 的措辞重跑。
  `tests/probe.js` 现在带有两个处境,对应两条尚无证据的 v3 规则:单元测试是错误的检查手段,以及一次修复长出了
  新机制;这里没有记录任何一个的结果。
- **未覆盖的那一类依然未覆盖。** 探针只跑对照臂,所以没有任何东西能检测到 skill 把一个有能力的模型从正确的
  默认判断上推开。
- **砍掉的东西带着点名的风险。** 限定范围的复查可能漏掉一次修复在它所读的那些行之外造成的缺陷。没有独立
  上下文时,由作者自己驱动这条路径,他可能看到的是自己预期的东西;交接里要说明这一点。

v2.7.0 依然可达:`git checkout v2.7.0`,或者它的 release 上附带的 `.skill`。
